# ADR-005: Mantener re-extracción completa en vez de ingesta incremental de Overpass

- **Estado:** aceptado (descartada la ingesta incremental para el alcance actual).
- **Contexto:** el pipeline re-extrae en cada corrida todo lo que coincide con `nwr[amenity=cafe]({bbox}); out center tags;` sobre un bbox provisional de la ZMG (`config/sources.yaml`); `render_query` solo sustituye el bbox y `extract_offline`/`extract_live` no guardan cursor de "última extracción". La deduplicación determinista (M2) y el upsert por `source_id` en una transacción (M4, con rechazados auditables por `V2__partial_unique_accepted_identity.sql`) ya toleran reextracciones repetidas sin duplicar. El volumen esperado es de decenas o centenas de objetos (no se midió en vivo para este ADR; la validación operativa usó 4 cafés de fixture) y el proyecto es educativo, sin restricciones reales de cuota o costo.
- **Opciones evaluadas (documentación oficial de Overpass):**
  - Filtro `newer:"fecha"`: según [Overpass QL](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL), "selects all elements that have been changed since the given date" y "cannot be used alone". Compara contra la última modificación de cada elemento y es acumulativo desde esa fecha hasta el estado actual; no es un diff entre dos extracciones. Como se aplica sobre el estado actual, un café borrado o que dejó de tener `amenity=cafe` no aparece en el resultado: el filtro no detecta salidas (inferencia; la página no documenta borrados explícitamente). `changed:"f1","f2"` es la variante por intervalo recomendada cuando hay datos attic.
  - Salida `[adiff:"fecha"]`: el mismo documento indica que marca elementos borrados con `visible=false` y los que "no longer match the query" con `visible=true`. Sí detecta salidas, pero depende de datos attic del servidor y obliga a parsear un formato distinto (old/new) al actual `out center tags`.
  - [Augmented diffs](https://wiki.openstreetmap.org/wiki/Overpass_API/Augmented_Diffs) (`/api/augmented_diff?id=…&bbox=…`): un diff por minuto con estado inicial y final de cada elemento (create/modify/delete), pensado para mantener bases especializadas actualizadas minuto a minuto y usado por herramientas de QA de ediciones (OSMCha, achavi, osm-revert). Acepta `bbox`, pero no filtra por tag: ponerse al día tras N días exige ~1 440·N peticiones y filtrar `amenity=cafe` del lado cliente. Es desproporcionado para una sola categoría en un bbox pequeño.
- **Decisión:** descartar la ingesta incremental mientras se mantengan las condiciones del contexto. La re-extracción completa sigue siendo el único modo: es una sola consulta pequeña, el pipeline ya es idempotente y, a diferencia de `newer`, entrega el conjunto completo vigente, condición necesaria para saber qué objetos dejaron de coincidir con la consulta.
- **Consecuencias:** no hay que mantener cursor, datos attic ni un segundo formato de parseo, y cada snapshot raw sigue siendo autocontenido (ADR-002). Se paga reconsultar objetos sin cambios, lo cual es aceptable a este volumen. Limitación vigente que este ADR no resuelve: `load_run` solo inserta o actualiza y no retira de `analytics.cafes` los `source_id` ausentes en la última corrida. La re-extracción completa permite detectarlos comparando conjuntos, pero eso requiere un issue propio fuera de M8. Este ADR no implementa nada. **Resuelto por ADR-006 (issue #49).**
- **Reabrir si:** el área crece a escala estatal o nacional, se agregan muchas categorías, aparecen límites de cuota o rechazos (429/timeouts) recurrentes de Overpass, o se adopta un scheduler (ADR-003) con frecuencia de minutos u horas.
- **Alternativas descartadas:** `newer`/`changed` con cursor (no detectan salidas y añaden estado); `adiff` con fecha (detecta salidas, pero agrega dependencia de attic y un parser nuevo sin beneficio a este volumen); augmented diffs minutales (pensados para replicación y QA continua, no para un recorte de una categoría).
- **Límites de la investigación:** el comportamiento de `newer` ante borrados se infiere de que filtra el estado actual; no se probó contra una instancia de Overpass. Tampoco se verificó qué instancias públicas conservan datos attic ni por cuánto tiempo.
